How banneret works

A playbook and three agent contracts, compiled into Claude Code or Codex. One session builds; sub-agents only read and check. Every rule in the playbook came from a trial run.

Figure 1 · one /pipeline run

Who does what in a run

THE HINGE

Everything checks one pinned commit

Before any verifier starts, the session commits, runs every test tier, and names the full SHA in each brief. Any later change makes old verdicts stale, so each fix goes to the 3b round with both SHAs and the diff between them.

Sub-agents read and check

  • Scouts only for foreign context, never files you'll edit
  • Verifiers return CONFIRMED / REFUTED / PLAUSIBLE with evidence
  • Each gets its own mktemp -d copy, in the foreground
  • A repo's own writing agents run report-only

Integrate is never skipped

Full suite with no verifier running, spec reconciled with what shipped, and one end-to-end diff read, comments included. In the last two trials that read caught defects no verifier flagged.

WHAT'S REALLY CODE

Compile is the only code; the rest is contract

src/compile.js maps each file's frontmatter to a target: .claude/agents/ and commands/pipeline.md (scouts on haiku), or .codex/agents/*.toml plus a managed AGENTS.md block. Only Codex enforces read-only, through sandbox_mode. In Claude Code, "sub-agents never write" holds because the agent follows the prose.

Every rule has a trial

  • reeve, lead-scoring-crm, framesmith
  • Each rule carries its trial-data note
  • Proposals that don't hold up are dropped in the PR
